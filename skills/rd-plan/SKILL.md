# 方案对比与计划

直接写计划的人，通常只想到了第一个办法。先摆出候选，再选。

## 什么时候做

- L2/L3 任务，尤其是「改法不止一种」的：换库不换库、抽不抽公共层、同步还是异步。
- 需求清楚但边界模糊：先各做一个方案，边界自然清楚了。
- L1 不用做，直接改。

## 第一步：给 2–3 个方案

每个方案写四行，不要更多：

```
方案 A：<一句话做法>
  代价：<改几个文件 / 加不加依赖 / 破坏兼容吗>
  好处：<解决什么>
  放弃理由或选择理由：<一句话>
```

**三条硬要求**：

1. **至少两个方案**，且必须真的不同——不是「方案 A：用 X；方案 B：用 X 但改个名字」。
2. **写清放弃理由**。只列好处不列代价的，等于没比较。
3. **至少一个「什么都不改」或「最小改动」的对照项**，否则容易过度设计。

## 第二步：选，并说清为什么

选择标准按优先级：能验证 > 改动面小 > 与现有约定一致 > 性能 > 优雅。

**不要**用「更优雅」「更现代」当理由——那不是理由，是偏好。

## 第三步：把选中的方案写成计划

```
目标：<一句话>
步骤：1) … 2) … 3) …（每步可单独验证）
风险：<最可能出问题的地方，以及怎么发现>
回滚：<改坏了怎么恢复；写清命令>
不做：<明确排除的相邻问题>
```

**回滚点必须具体**：`git revert <sha>`、恢复某个备份文件、关掉某个开关。写不出来说明计划还没想清。

## 四条反面清单

| 别这样 | 改成 |
|---|---|
| 只写一个方案就开工 | 补两个，哪怕第二个是「最小改动」 |
| 「方案 B 更好」但不说好在哪 | 写出可比较的指标：改动文件数、是否加依赖、跑多久 |
| 计划里每步都是「继续完善 X」 | 每步要能单独验证：跑什么命令、看什么输出 |
| 风险写「可能有问题」 | 写「如果 X 发生，会在 Y 处看到 Z」 |

## 与流水线的衔接

- S1 规格卡里的「范围」由方案对比产生：选中方案要做的是「做」，被放弃的是「不做」。
- 计划写完先给用户确认（L3 必须），再进 S4 实现。
- 计划里的回滚点，在 S5 验证时顺手验一次「回滚命令真的存在」。
