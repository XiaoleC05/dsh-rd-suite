# KPI 定义与解读

数据来源：DSH 会话页显示的用量（每条消息的上下文、缓存命中、输出）与交付报告中的验收表；本仓库不再附带统计脚本，指标由模型在复盘时人工汇总，用于看趋势而不是精确计量。下表「基线」一列来自 2026-11-19 的一次统计（引入研发模式之前、全部模式），只作参照，不是当期目标。当期目标写在 `docs/DESIGN.md` 的 KPI 表中，改动目标值要按 rd-retro 的提案流程走。

|---|---|---|---|
| K6 | 工具调用失败率 | 1.9% | 看报告“工具”表中失败最多的工具：路径错误、编辑未匹配、网页重定向等 |

## 流程合规与质量（按任务段统计）
任务段 = 顶层会话中从一条用户消息到下一条用户消息；分级沿用会话中最近一次【L…】标记；K9–K11 只统计改了文件（edit / write / apply_patch）的任务段。

| 编号 | 定义 | 基线 | 解读 |
|---|---|---|---|
| K9 | 改了文件的任务段中已标注分级的占比 | 0%（41 个任务段；旧模式没有此规则） | 低于 90% 说明宪章 §2 没有被遵守，优先在 suffix 自检区强化。报告中“标为 L0 却改了文件”大于 0 说明分级偏低 |
| K10 | L1–L3 任务段的最终回答带验收段落（**验收** 或“验证：”）的占比 | 无数据 | 低说明 S5/S7 关卡被跳过 |
| K11 | L3 任务段调用过 review_agent 的占比 | 无数据 | 低说明 S6 被跳过；也对照 L3 数量判断是否分级偏低 |
| K12 | 顶层用户消息中含纠正类措辞的占比 | 7.9% | 关键词启发式，只看趋势；上升时结合抽样会话找原因 |

## 辅助信号（报告中给出，不设目标）
- 每条用户消息的 LLM 请求数（基线 35.5）：骤增可能表示反复试错或子任务拆分过细。
- 首轮请求上下文的中位数（历史值：standard 约 10.3k、ptc 约 18.3k；现在的 rd 含 PTC，估计 18–21k）：用来发现宪章与工具定义的膨胀。
- Shell 非零退出率（基线 7.4%）：上升时看是否为 Windows 路径、编码或缺少工具。
- 技能加载次数：长期为 0 的技能说明描述不清或确实没用，考虑合并或删除。
- 验收结论分布（PASS / FAIL / UNVERIFIED）：UNVERIFIED 多说明验证命令在子代理中跑不起来，检查任务说明是否给全了命令与工作目录。
- 消息反馈（当前有效的好评与差评）与 Crisp 结果：Crisp 日志不区分模式，只作整体参考。

## 抽样评审（每次复盘）
每期挑 3 个会话：上下文最大、出现返工信号、随机各 1 个。只读它们的用量数字与交付报告，不读会话原文；每个会话按 5 项各 0–2 分，指标无法判断的项写“需人工查看”，并请用户在工作区与开始时间对应的会话里自行核对：
1. 分级是否恰当：有分级标记；“标为 L0 却改了文件”为 0。
2. AC 与证据：L2/L3 会话的 AC 编号数 ≥ 1；验收段落数不少于交付次数；review_agent 的结论没有未处理的 FAIL 或 UNVERIFIED。
3. 改动范围与规范：需人工查看。
4. 报告质量（结论先行、证据完整、没有空话）：需人工查看；Crisp 启用时参考其结果。
5. Token 纪律：平均上下文 ≤ 120k、重复读取 ≤ 2、超大结果 ≤ 1。
评分只用于发现问题与生成提案。不要自行解码、读取或输出会话日志原文；需要人工查看的项，请用户按表中的工作区与开始时间在会话列表中打开对应会话。
