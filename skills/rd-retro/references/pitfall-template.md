# 踩坑记录格式

写进长期记忆时用 `type: pitfall`，正文按下面五段。缺段的记录下次搜到了也用不上。

## 一、现象

用户或测试实际看到什么：报错原文、错误码、界面表现。
**不要写**「有点问题」「不太对」——这类描述无法被检索，也无法判断是否同一个坑。

## 二、触发条件

什么情况下必然复现：命令、输入、数据量、平台、并发数。
**要写**可重跑的步骤；只在特定机器上复现的，写清那台机器的关键差异。

## 三、根因

代码或流程里真正出错的那一处，附 `文件:行`。
**不要停在**「缓存没清」这种中间结论——继续问一句「为什么没清」，写到能改的地方为止。

## 四、修复

改了哪几处、为什么这样改、有没有副作用。
**不要只写**「已修复」——下一个人需要判断这个修复适不适用于他的场景。

## 五、防复发检查

一条能被机器或流程执行的检查：测试名、lint 规则、脚本断言、CI 门禁。
**不要写**「以后注意」「加强评审」——这些不是检查，只是愿望。

## 适用边界

这套写法的前提是坑能被复现。纯环境问题（网线松了、证书过期）把它标成 `pitfall` 也可以，
但第三节要如实写「环境，非代码」，别硬编一个技术根因。

## 一条填好的例子

```
现象：push 报 curl 56 Recv failure: Connection was reset，换个仓库同样报。
触发条件：本机 git 走系统代理 127.0.0.1:7890；gh 能通，git 不能。
根因：git 没读系统代理配置（libcurl 不看 WinINET），且 schannel 后端在代理下握手失败。
修复：给 github.com 单独配 http.proxy，并把 http.sslBackend 换成 openssl。
防复发检查：scripts/git-net-check.mjs 四项校验，测试 test/git-net-check.test.mjs 覆盖判定规则。
```
