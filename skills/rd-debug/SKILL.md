# 结构化调试

乱改代码碰运气，通常会把一个问题变成三个。按顺序走四步。

## 一、复现：先让它稳定失败

**目标**：拿到一条能重复执行的命令，失败率 100%。

- 记下失败的**原始输出**：错误码、堆栈、断言差异。不要先解释，先留证据。
- 缩小输入：数据量、并发数、文件数、时区、locale、换行符。
- 只在特定机器出现时，先比对这些：Node/运行时版本、依赖版本、环境变量、路径大小写、文件系统。
- **做不到稳定复现就先别改代码**——修一个不能复现的问题，等于改运气。

写下来：

```
复现命令：<一行>
失败输出：<关键 3–5 行>
稳定度：100% / 偶发（多少次里几次）
```

## 二、定位：找到能改的那一处

**目标**：把现象追到「改了这里，现象就消失」的具体位置。

三种手段按成本排序：

1. **缩短调用链**：从入口往里打日志/断点，二分定位到出错的那一段。
2. **对照法**：把错误输入的某个维度换成正常值，看现象是否消失——消失的那一维就是边界。
3. **差异对比**：同一份代码在能跑与不能跑的环境各跑一次，diff 输入、配置与依赖版本。

**根因链要求**：不要停在中间结论。「缓存没清」不是根因；「缓存键用了反斜杠、与写入时的正斜杠不匹配，所以命中不了」才是。

写到 `文件:行` 级别的结论：

```
根因：<文件:行> 的 <做什么> 与 <另一边> 不一致
证据：<复现命令的哪一行输出> / <两处代码的差异>
```

## 三、修：最小改动

- **只改根因那一处**。顺手重构、顺手加日志、顺手改风格，都留到另一次提交。
- 修之前先想：这个修法会不会把问题挪到别处（换了个触发条件）？
- 边界条件补上：空值、零条、超长、并发、重复调用。
- 修完**重跑第一步的复现命令**，要看到它变成通过。

## 四、防复发：补一条会红的测试

- 测试要能在**旧代码上失败**——写完先在旧实现上跑一遍，确认它真的会红。
- 测试名写清「什么条件下会怎样」，不要写 `test('fix bug')`。
- 断言具体值，不写「不抛错即通过」。

## 四条反面清单

| 别这样 | 为什么 | 改成 |
|---|---|---|
| 先改代码再想为什么 | 会掩盖真因，问题复现时更难查 | 先复现，留原始输出 |
| 一次改五处 | 不知道哪一处生效，也不知道哪一处引入新问题 | 一次一处，逐步验证 |
| 删掉失败断言让它变绿 | 把问题藏起来 | 改实现，不改期望值 |
| 「重启后就不复现了」当结论 | 没解释的消失会再回来 | 记进记忆：现象、怀疑的触发条件、下次怎么抓 |

## 与流水线的衔接

- 缺陷类任务的分级按影响面：能稳定复现且影响交付 → L2；涉及数据损坏、权限、并发 → L3。
- 第二阶段结论写进规格卡的「问题」一节；第四阶段的测试就是 AC 的证据。
- 修完把「现象 → 根因 → 修法 → 检查」按 `rd-retro` 的踩坑格式存进长期记忆。
