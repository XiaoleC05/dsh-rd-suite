# 规格产物（rd-spec）

做法来自 github/spec-kit：先把「要什么」写清楚，再写「怎么做」，最后拆成可勾的任务。
与宪章的关系：S1 规格卡是这三份文件的摘要，不替代它们；L2 用规格卡就够，L3 才落文件。

## 1 何时用

- L3 任务（新模块、公共接口、数据迁移、安全与权限、并发、部署）。
- 需求有歧义，或用户只给了目标没给验收标准。
- 任务要跨会话继续，下一轮的人（或子代理）需要不靠对话就能接手。
- L1/L2、纯问答、只改一处文案：不落文件，规格卡足够。

## 2 产物与位置

```
specs/<NNN>-<slug>/
  spec.md     要什么：问题、范围、验收标准 AC、约束、不做什么
  plan.md     怎么做：技术方案、改动清单、依赖与风险、回滚
  tasks.md    按什么顺序做：勾选清单，每条挂到 AC
```

`<NNN>` 用三位序号（从 001 开始，取目录里已有最大值加一），`<slug>` 用小写短横线。目录放项目的 `specs/` 下；项目已有规格目录时沿用项目既有位置。

模板在 `references/spec.md`、`references/plan.md`、`references/tasks.md`，直接复制再改，不要另起格式。

## 3 四个动作

1. **clarify（前）**：把只能由用户决定的事一次问清，最多 3 问，每问带推荐项。能靠读代码、跑命令查明的自己查，不要问。
2. **analyze（中）**：写完 spec 与 plan 后交叉核对：每条 AC 是否在 plan 里有对应改动、tasks 是否覆盖每条 AC、有没有 plan 里出现但 spec 没要求的东西。发现缺口先补 spec，再改 plan。
3. **checklist（开工前）**：五问过一遍——AC 能由命令判定吗？范围写了不做什么吗？风险与回滚写了吗？tasks 每条都能独立验证吗？三份文件的术语一致吗？
4. **converge（收尾）**：实现完成后回填 tasks 的勾选与证据，把 plan 里没做的项标成「未做 + 原因」，再按宪章 S7 写交付报告。

## 4 边界

- 规格是承诺，不是许愿：写进 AC 的必须能验证；验证不了的降级为「观察项」。
- 不复制整段需求原文，用自己的话重述，长的引用放附录并标出处。
- 不做的事要写清楚，避免范围悄悄扩大；范围变化先改 spec，再动代码。
- 与 rd-testing 的关系：AC 的验证命令由 rd-testing 的选型表决定，spec 只写「怎么判定通过」。
