# 面向用户的发布说明

CHANGELOG 写给维护者：文件名、函数名、用例数。发布说明写给用户：**我这边会有什么不同**。

## 四段结构

### 一句话变化

这次升级之后，用户能感知到的那一件事。不超过两行。

### 你会遇到什么不同

按「原来 → 现在」写，每条都能在界面上或命令输出里看到。
不要写内部实现（「重构了 audit.js」），写可观察结果（「模块关闭时会自动改文件」）。

### 需要你做什么

要改配置、要重跑命令、要清缓存，逐条列出并给命令。
不需要动手就写「无需操作」——这一句能省掉大量追问。

### 已知问题

还没解决的、会影响使用的，如实写；没有就写「已知问题：无」。
**不要**写「持续优化中」——那不是已知问题，是安慰。

## 措辞规则

- 不用「优化」「完善」「提升整体」这类词，改用数字或行为变化；
- 每个版本最多一个「一句话变化」，多了说明这次发布该拆开；
- 已知问题里如果条目超过三条，先修再发。

## 草稿怎么来

```
node scripts/release-notes.mjs --version 0.66.1
```

脚本从 CHANGELOG 取对应版本块，按新增 / 修复 / 文档分桶后套上面的四段，
占位段落需要人补：一句话变化与「需要你做什么」机器猜不出来。
