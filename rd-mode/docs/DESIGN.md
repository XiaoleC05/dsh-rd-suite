# 研发模式（dsh-rd-mode）设计说明

| 项目 | 内容 |
|---|---|
| 版本 | 0.1.0（2026-11-19） |
| 适用 | DeepSeek Harness Desktop 0.2.2-rc.5（Windows x64） |
| 日常执行者 | DSH 中的 DeepSeek V4.1（deepseek-flash） |
| 读者 | 用户（审阅与决策）；DeepSeek V4.1（实施与维护，操作步骤见仓库根目录 INIT.md） |
| 位置 | D:\05_Code\dsh-rd-suite\rd-mode |

## 0 结论摘要

研发模式是一个只含配置与文档的 DSH bundle，声明三个新预设：**研发模式 rd**（主模式）、**研发·侦察 rd-scout**（只读侦察子代理）、**研发·验收 rd-review**（独立验收子代理），不覆盖任何内置模式。它用五个机制回应三个痛点：

1. **分级流水线 + 两道关卡**（针对质量波动）：每个任务先分级 L0–L3；L2 以上必须有可判定的验收标准（AC），交付前必须给出实际运行的证据；L3 必须经过不带作者上下文的独立验收。
2. **常驻宪章 + 按需技能**（针对规则难约束）：约 4.1k 字符的宪章常驻系统提示词；编码、测试、网站与文案、数据、AI/Agent 等领域标准做成技能，只在任务匹配时加载。
3. **上下文治理**（针对 Token 浪费）：压缩阈值从约 727k 提前到约 199k；收紧单次工具输出；侦察放进子代理；去掉 PTC 与低价值工具定义。
4. **评价体系**：运行时关卡 + 独立验收 + 从会话日志计算的 12 项 KPI（已生成基线）+ 抽样评审 + 基准任务集。
5. **受控进化**：每周复盘生成带证据的改进提案，用户批准后才应用；改动经校验器检查、版本化、可回滚。

交付前已做的验证：用 DSH 自带运行时按每个插件自己的配置 schema 校验全部预设行（0 错误）；在隔离的 DSH 0.2.2-rc.5 宿主中以 link: 方式安装本 bundle 并启动，预设注册表报告 rd、rd-scout、rd-review 三个预设均激活成功；技能目录表达式能解析到本包的 skills 目录；KPI 脚本通过合成日志回归测试。随后经三路独立复核（DSH 事实核查、按手册模拟执行、宪章对抗审查）共 60 条意见（无阻断项），已据此修订宪章、手册、技能与脚本。

预期效果（第一个月目标，由 KPI 验证）：平均每次请求上下文从 319,202 降到 120,000 以下；超过 200k 的请求从 66.2% 降到 5% 以下；L1–L3 交付带验收证据的比例达到 90% 以上。

## 1 现状诊断（证据）

### 1.1 用量数据
来源：`%USERPROFILE%\.dsh\sessions` 中 49 个会话（2026-11-17 至 11-19；18 个顶层、31 个子代理），统计脚本即本包的 `scripts/rd-kpi.mjs`，完整基线见 `evolution/kpi/baseline-2026-11-19.md`。

| 指标 | 数值 |
|---|---|
| LLM 请求 | 5,062 次（顶层 2,700，子代理 2,362）；每条用户消息平均触发 35.5 次请求 |
| 上下文 token 合计 | 16.16 亿，其中命中缓存 99.13%，未命中 0.87%；输出 690 万 |
| 每次请求的上下文 | 平均 319,202；p50 287,874；p90 626,255；最大 728,115 |
| 上下文分布 | 200k–400k 占请求 31.8%；400k 以上占 34.5%，却消耗了全部上下文 token 的 59.7% |
| 上下文增长 | 顶层会话中位数：第 0–9 步 35k，第 50–99 步 310k，第 200–399 步 618k（每步约增长 3.9k） |
| 压缩 | 49 个会话只触发 3 次。阈值 = min(1,048,576 × 0.8, 1,048,576 − 256,000 − 65,536) = 727,040 |
| 工具输出 | read 占全部工具结果字符的 46.9%，pwsh 20.6%，run_code 19.4%，cordis_inspect_query 6.3%；超过 2 万字符的结果 251 个；重复读取未变化文件 44 次（另有 94 次是改动后的复核读取） |
| 固定前缀（首轮请求） | ptc 顶层约 18.3k；standard 约 10.3k |
| 质量信号 | 顶层用户消息中 6/76（7.9%）含纠正类措辞；8 个轮次以错误结束；Crisp 89 次检查全部通过，但 11-17 之后没有再运行 |

成本结构：缓存命中虽然便宜，但量是未命中的 114 倍。按 DeepSeek 常见的价格比例（未命中 ≈ 命中的 10 倍、输出 ≈ 命中的 15 倍，请以实际账单单价为准）估算，命中缓存的上下文约占总成本的 87%，未命中约 8%，输出约 6%。因此**缓存命中率已经不是杠杆，真正的杠杆是每次请求携带的上下文长度乘以请求次数**。推理强度（reasoningEffort）影响的是输出，占比很小，所以主代理保持 max 不会显著增加成本。

### 1.2 环境发现
- 当前默认模式是 PTC（selectedDefault: ptc）：首轮前缀比 standard 多约 5k token，且不挂载 plugin_manager。
- 会话可发现的用户技能为 0。用户的 35 个技能（superpowers、planning-with-files 等）在 opencode 与 piagent 的目录下，另有 10 个在 D:\06_Projects\Skills，都不在 DSH 的扫描路径中。
- Crisp 质量门禁已作为依赖安装，但不在 `dsh.profile.bundles` 中，profile 里为它写的配置被加载器跳过，门禁没有运行。
- 权限为 danger-full-access 且不弹审批：文件、网络与进程都不受限，安全只能依靠指令层面的红线。
- 所有会话（包括子代理）都以 reasoningEffort: max 运行。
- 用户已经写好的标准：code-pipeline 的 10 种语言预设、dsh-code-style 的审查原则与优先级、Crisp 的回答质量细则、pro-prompt 的 C1–C9 任务输入约束、github-issue-first 的“一模块一 issue 一提交”流程、solo-bench 的独立审计报告格式、Confluence 的工作区记忆模型。本设计直接复用它们，不另起炉灶。

### 1.3 根因
质量波动：
1. 没有显式的完成标准，“做完了”由模型自行判断。
2. 没有强制的验证证据，未运行的检查可能被描述为通过。
3. 上下文长期处于 30 万到 70 万 token，越到会话后段指令越容易被稀释。
4. 规则对模型不可见：没有可发现的技能，默认工作区也没有 AGENTS.md。
5. 唯一的回答质量门禁没有在运行。

Token 浪费：
1. 压缩阈值过高，等于不压缩。
2. 一个会话承载多个主题（顶层会话最多 21 轮、675 次请求）。
3. 整文件读取与无界命令输出进入历史后，被每一步重复发送。
4. 侦察与资料调研在主上下文中进行。
5. 默认模式的固定前缀偏重。

## 2 设计原则
- **P1 质量 = 规格 × 验证 × 独立复核**，而不是提高推理强度。
- **P2 成本 ∝ 每次请求的上下文 × 请求次数**，控制上下文长度比提高缓存命中率重要。
- **P3 结构优于说教**：固定的分级、关卡、模板和输出格式压低方差。
- **P4 常驻最小、细节按需**：宪章只写所有任务都需要的规则，领域细则放进技能。
- **P5 复用已有资产**：用户自己的插件和标准优先于新发明。
- **P6 进化可度量、可审批、可回滚**：没有证据不改，没有批准不改，改了能退回。
- **P7 诚实优先**：没运行就是未验证；检查跑不了要说出来，不能当作没问题。

运行时数据流：用户任务 → 分级 → 规格卡 → 计划 → 实现 → 验证 → （独立验收）→ 交付报告 → 会话日志。
进化数据流：会话日志 → rd-kpi → rd-retro 诊断 → 提案 → 用户批准 → 修改 bundle → 校验 → 重新组合 → 新会话生效 → 下期 KPI 检验效果。

### 3.1 关键决策
| 决策 | 选择 | 备选与放弃理由 |
|---|---|---|
| 模式载体 | 新的预设 bundle | 覆盖内置 standard：覆盖会整体替换插件列表，此后永远收不到官方更新，也失去内置模式这一退路 |
| 工具执行方式 | 原生工具 | PTC：首轮前缀多约 5k token，run_code 失败率 4.2%，用户插件在 PTC 下的可达性未验证；保留为 A/B 实验 |
| 规则放在哪里 | 宪章放 persona；领域细则放技能；项目约定放各仓库的 AGENTS.md | 全局 AGENTS.md 会影响所有模式；全部写进 persona 会让常驻前缀膨胀 |
| 角色分工 | 子代理预设（spawn） | workflow 工具：官方文案限定仅在用户明确要求时使用；Agent Team：多出 4 个工具与常驻策略段，适合 3 个以上并行写入者，本场景不需要 |
| 记忆 | 复用 Confluence 的看板与画像 | 自建记忆：重复建设 |
| 回答文风质量 | 复用 Crisp，交付模板对齐其细则 | 再加一轮模型自评：与 Crisp 的评审重复，每次回答多花约 1.8k token |
| 进化方式 | 提案 + 用户批准 | 自动自改：没有外部校验时容易漂移，而预设一行出错就会让整个模式不可用 |
| 语言 | 宪章与技能用中文，标识符保持英文 | 用户的输入与 Crisp 改写指令都是中文；DeepSeek 对中文的处理成熟 |

## 4 工作流规范

### 4.1 任务分级
| 级别 | 判定条件 | 必经阶段 | 交付形式 |
|---|---|---|---|
| L0 问答 | 不改文件 | 直接回答 | 引用 `文件:行`，不套模板 |
| L1 微改 | ≤ 2 个文件、意图明确、低风险 | 定位 → 修改 → 最小验证 | 结论 + 一行“验证：命令 → 结果” |
| L2 标准 | 多文件功能或缺陷修复，需求清楚 | 简版规格卡 → 计划 → 实现 → 验证 | 完整报告模板 |
| L3 复杂/高风险 | 新模块；架构、公共接口、数据结构或迁移；安全、鉴权、支付、权限；并发；CI、部署、生产配置；需求不清 | 规格卡与计划一次提交批准 → 分模块实现与验证 → 独立验收 | 完整报告模板 + 验收结论 |

规则：发现风险或范围扩大立即升级；不得为跳过关卡而降级；凡涉及 L3 所列风险项即为 L3。新任务的第一条回复写出【L1–L3｜理由】（L0 问答与同一任务的后续轮次不写），这既约束模型，也让 KPI 可以统计。

### 4.2 流水线与关卡
| 阶段 | 内容 | 关卡 |
|---|---|---|
| S1 规格卡 | 目标｜范围（做/不做）｜验收标准 AC-1…n｜约束｜风险 | G1：每条 AC 都能由命令输出或可观察结果判定 |
| S2 侦察 | AGENTS.md、CLAUDE.md 已自动注入，不再重复读取；按需读 README 与构建、测试脚本；定位后再读行段；大范围交给 rd-scout | — |
| S3 计划 | 计划模式中各级任务只出计划，用 exit_plan_mode 一次提交规格卡与计划；否则 L2 用 todo_write，L3 在同一条回复给出规格卡与计划，用 ask_user_question 请求批准 | — |
| S4 实现 | 先读后改、沿用既有风格、只做规格内改动、不留临时方案 | — |
| S5 验证 | 亲自运行证明每条 AC 的命令；缺陷先复现再修并留回归测试 | G2：每条 AC 有本会话的真实证据，或明确“未验证：原因” |
| S6 独立验收 | review_agent 拿到规格卡、改动清单、验证命令后独立复核；复审用 send_message 发给原验收子代理，最多一次 | G3：没有 BLOCKER；UNVERIFIED 的 AC 标为未验证（L3 必做） |
| S7 交付 | 报告模板（见 4.4） | 交付前自检（suffix） |
| S8 沉淀 | 经验写入 Confluence；规则缺陷只提建议 | — |

### 4.3 完成定义（代码验收标准）
- **L1**：改动能运行或编译；相关测试或最小验证命令通过；没有无关改动。
- **L2**：L1 全部条件；每条 AC 都有证据；新增或修改的行为有测试，缺陷修复有回归测试；项目定义的构建、lint、类型检查全部通过；改动文件已格式化；没有 TODO、调试输出与死代码；相关文档和配置已同步。
- **L3**：L2 全部条件；review_agent 结论为 PASS（结论为 UNVERIFIED 时，相应 AC 在报告中标为未验证）；接口或数据变更附迁移与兼容说明；写明风险与回滚方式。
- 任何级别：检查无法运行时如实标注“未验证”，并给出用户可以自行执行的命令。

### 4.4 模板
规格卡（S1）：
```
【L2｜两个文件以上，需求清楚】
目标：登录失败 5 次后锁定账号 15 分钟
范围：做——auth/service.py 计数与锁定、对应测试；不做——前端提示文案
验收标准：
  AC-1 pytest tests/test_auth_lock.py 全部通过
  AC-2 第 6 次错误登录返回 423，并在响应中给出解锁时间
  AC-3 锁定期内正确密码也返回 423；15 分钟后可正常登录（用可注入时钟测试）
约束：不新增依赖；沿用现有 Redis 客户端
风险：并发登录下的计数竞态
```
交付报告（S7）：
```
**结论**：已实现登录失败锁定，3/3 条验收标准通过。
**改动**：`auth/service.py` — 新增失败计数与锁定检查；`tests/test_auth_lock.py` — 4 个用例
**验收**：
| AC | 验证方式 | 结果 |
| AC-1 | pytest -q tests/test_auth_lock.py | 通过（4 passed） |
| AC-2 | 用例 test_lock_after_5_failures | 通过（423，含 unlock_at） |
| AC-3 | 用例 test_unlock_after_15min（注入时钟） | 通过 |
合计 3/3 通过；未验证 0 项
**风险与未完成**：计数用 Redis INCR，已覆盖并发；未做前端提示
```
验收结论（rd-review 输出）：首行 `VERDICT: PASS|FAIL|UNVERIFIED`，随后逐条 AC 的证据、BLOCKER / MAJOR / MINOR、疑点、已运行的命令，总共不超过 40 行。

### 4.5 与用户已有插件的衔接
- **github-issue-first**：设置中开启后，其系统提示段（order 700）规定的“预检 → 每模块一个 issue → 每模块一个经验证的提交 → 关闭 issue”优先于模式自身的提交习惯；但预检提示有未提交改动时先问用户，不自行 commit 或 stash（安全红线优先）。
- **code-pipeline**：仓库没有自己的格式化配置时，对改动文件先 report 再 fix；仓库有配置时运行仓库命令（code-pipeline 不读取仓库配置，且 JS/TS 预设为单引号无分号）。
- **Confluence**：跨会话继续任务前查看工作区看板；中途结束时发一条 handoff；用户长期偏好写入画像。
- **Crisp**：交付模板与 Crisp 的细则一致（结论先行、无铺垫与重复、不删必要事实），因此它通常直接放行；不再增加模型自评环节。
- **pro-prompt**：用户经它的 structure 模式发来的任务已经分节，其中“验收标准”一节直接作为 AC 使用。

### 4.6 计划模式与 /goal
- 计划模式只能由用户用 `/plan` 进入；进入后按官方规则用 exit_plan_mode 提交计划。本模式在官方文本后追加一段：计划要以规格卡开头、按模块列步骤、每步写明对应 AC 与验证命令。
- 长任务自动续跑：用户在对话中直接要求时，模型用 create_goal 并把 AC 写进 objective，续跑的每一轮都会重新看到它。用户用 /goal 设定的目标，模型在续跑轮次中无权改写（update_goal 的 edit 需要用户本回合直接要求），AC 记在规格卡与 todo_write 中。收尾时官方的 wrap-up 要求说明“如何验证”，与 G2 一致。

## 5 分领域规则

| 领域 | 技能 | 核心标准 | 验证方式 |
|---|---|---|---|
| 编码与审查 | rd-code-standards | 规范优先级（项目配置 > 框架工具 > 语言官方 > 框架建议 > 工具默认）；格式化只针对改动文件且幂等；通用编码规则；各语言速查；安全编码；人工审查清单；Conventional Commits | 格式化、lint、类型检查命令 |
| 测试与调试 | rd-testing | 最小充分验证选择表；系统化调试（复现 → 定位 → 根因 → 修复 → 回归，3 次假设失败即停）；以需求命名的测试、确定性、禁止改期望值；Windows 下的精简输出与后台运行 | 证据表 |
| 网站与文案 | rd-web（含 landing-copy.md、frontend-checklist.md） | 开工前确认项；落地页 8 段结构；标题写结果不写功能、功能写成收益、动词开头的唯一主 CTA、证据真实可查、禁用空话词表；语义化、响应式、WCAG 2.2 AA、性能预算（LCP < 2.5 s、CLS < 0.1、INP < 200 ms）、SEO | 构建、本地启动、截图检查、上线检查表 |
| 数据工程 | rd-data | 数据契约；幂等与回填；UTC；Join 行数核对；SQL 规范（禁 SELECT *、参数化、写操作先计数并确认）；向量化与惰性计算；6 项数据质量校验；可复现与隐私 | 小样本 → 断言 → 全量，报告行数与校验结果 |
| AI / Agent | rd-ai | 评测先行（≥ 20 条样例，含对抗与拒答）；提示词结构；工具设计原则；上下文与成本预算；RAG 评测；Agent 停止条件、防提示注入、可观测性；ML 实验可复现；时效信息以官方文档为准 | 固定评测集上的指标、成本与延迟 |

落地页文案标准是你特别提到的一项，要点如下（全文见 skills/rd-web/references/landing-copy.md）：
- 写作前必须明确读者、唯一主张（≤ 20 字）、唯一主转化动作和证据清单，缺一项先问用户。
- 标题写结果或改变（“把周报从 3 小时缩短到 10 分钟”），中文 8–16 字；副标题补充“怎么做到 / 给谁用”。
- 每个功能写成“功能 → 所以你可以 → 结果”；删除“领先的、一站式、赋能、颠覆、无缝”等空话；不写无法兑现的承诺。
- CTA 用“动词 + 结果”，按钮旁消除顾虑（必须属实），至少出现 3 次。
- 数据、评价、Logo 必须真实并注明来源；缺素材时用明显占位并在交付报告中列出待替换清单。

新增领域的方法：在 skills/ 下按同样格式新建技能（description 写清何时加载、正文 ≤ 6000 字符、细节进 references/），再在宪章 §4 的路由表中加一句。这是 C2 改动，走复盘审批。

## 6 Token 优化策略

### 6.1 成本模型
成本 ≈ Σ每次请求（命中缓存的上下文 × 1 + 未命中的上下文 × R + 输出 × P），R、P 为相对单价（默认 10、15，按实际价格调整）。在缓存命中率 99% 的前提下，第一项占主导，它取决于两个因素：每次请求的上下文长度，以及完成任务所需的请求次数。

### 6.2 杠杆
| 杠杆 | 具体做法 | 依据与预期 |
|---|---|---|
| 提前压缩 | compaction-basic：thresholdRatio 0.19（约 199k）、retainTokens 40000、summary maxTokens 32000 | 原阈值 727k 几乎不触发。新阈值下上下文在约 60k 与 199k 之间锯齿变化，平均约 120–130k；每约 35 步多一次摘要调用，摘要后有一次约 60k 的未命中重发，摊到每步约 2k 未命中。长会话成本预计下降约一半，同时避免超长上下文稀释指令 |
| 去掉固定前缀里的低价值部分 | 不挂载 PTC、workflow、schedule、subagent_fork、list_subagent_models | 相对 PTC 默认模式少约 5k token/请求；相对 standard 少约 2.5k，再加回 review_agent 约 0.4k 与宪章约 2.8k，整体略高于 standard |
| 收紧单次输出 | read 32 KB/次；grep 150 条、每行 600 字节；网页抓取 8 万字符、搜索 8 条 | 超过 2 万字符的结果占比偏高。read 超限时以截断提示结束，可用 offset 续读；grep 行预览超出部分直接截断；只有超过 12,500 token 的单个结果才进入溢出文件 |
| 宪章中的纪律 | 先定位后读行段；不重复读取未变化文件；命令输出有界（不截尾，利用工具保存的完整输出文件）；长测试前台运行并一次等待；合并搜索查询；UTF-8 文本只用 read | 针对 44 次重复读取与 251 个超大结果 |
| 侦察隔离 | 大范围探索交给 rd-scout，只带回 ≤ 40 行结论；子代理 effort=high，自身约 126k 即压缩 | 繁重的读取留在会随后丢弃的子代理上下文中 |
| 一个会话一个主题 | 宪章 §5.8：无关新任务建议新开会话 | 历史中顶层会话最多 21 轮 |
| 项目规则上限 | agent-instructions maxBytes 65536 → 24576 字节/链 | 规则文件常驻至压缩，最坏情况从约 32k token 降到约 12k |
| 技能按需 | 技能目录共 13 条（rd-* 7 条约 735 字符、dsh-doc、宿主注册的 office×4 与 Windows 沙箱诊断），连同固定说明约 2.6k 字符；技能正文 1.1k–2.5k 字符，只在 L2/L3 任务加载 | 领域规则不占常驻前缀 |
| 时间上下文 | refreshIntervalMs 10 分钟 → 1 小时 | 很小的收益，零风险 |
| 推理强度 | 主代理沿用全局 max；子代理 high；验收子代理 max | 输出约占成本 6%，主代理降档收益小、质量风险大 |

### 6.3 有意没有做的事
- 没有改全局的 spill-policy（单个结果内联上限 12,500 token）与 harness-dev-context（每次请求约 350 token 的 DSH 开发说明）：它们在宿主层，会影响所有模式。复盘若有证据，可作为 C3 提案。
- 没有把主代理降为 high：理由见上表。

### 6.4 如何衡量
K1–K5 直接衡量上下文与成本；K7、K8 衡量工具纪律；报告中还给出首轮请求的中位数，用来防止宪章与工具定义在进化中膨胀。

## 7 插件与 Skill 的调度与发现

### 7.1 调度
- **常驻路由**：宪章 §4 规定“哪类任务加载哪个技能”，§7 规定已安装插件工具的使用时机。显式路由比只靠技能目录的描述匹配更稳定。
- **技能目录**：每次请求附带 rd-* 技能、dsh-doc，以及宿主注册的 office×4 与 diagnose-windows-sandbox-acl 的名称和描述（每条 ≤ 300 字符）；描述写明“何时加载”，并注明 L1 微改不加载。rd-selftest 设为仅用户可调用，不占目录。
- **用户显式调用**：在消息中写 `/技能名`（例如 `/rd-web`、`/rd-retro`）会直接注入该技能。
- **项目与用户级技能**：保留 DSH 默认扫描路径（`<项目>\.dsh\skills`、`<项目>\.agents\skills`、`%USERPROFILE%\.dsh\skills`、`%USERPROFILE%\.agents\skills`），因此其他仓库自带的技能照常可用。

### 7.3 发现与引入（rd-ecosystem 技能）
- **触发条件**：用户提出要求；任务因缺少能力确实无法完成；复盘发现同类手工操作在多个会话中重复。先判断“现有工具加一个脚本”能否解决；普通任务中途不因“可能有更好的工具”而偏离任务。
- **候选来源**（按顺序）：本机已有但未接入的技能与 MCP → DSH 官方可选插件（list_bundles）→ MCP 配置型 bundle → 插件市场（用户启用后）→ 公开生态线索。
- **评估卡**：必要性、成本（约每个工具 150 token/请求）、风险、重叠、可逆性，各 0–2 分；合计 ≥ 7 且无 0 分才建议引入。
- **引入流程**：记录基线 → install_bundle 试装（严格按 application 与 nextStep 分支处理）→ 新会话中验证 → 计量前后 token → 决定保留或回退；每一步先获得用户同意。回退顺序：set_plugin 关单行 → set_bundle 关整个 bundle → remove_bundle。
- **沉淀**：会话中形成的可复用流程先在交付报告中提出，用户同意后写成 `evolution/proposals/skill-<名称>.md` 草稿，经复盘或用户批准后移入 skills/ 并运行校验。

## 8 评价体系

### 8.1 三层结构
| 层 | 由谁执行 | 时机 | 判定方式 |
|---|---|---|---|
| 实时关卡 | 主代理 | 每个任务 | G1 AC 可判定；G2 每条 AC 有真实证据；交付前自检 |
| 独立验收 | rd-review 子代理（无作者上下文，effort=max） | L3 必做；涉险 L2 | VERDICT 与分级问题；亲自重跑验证命令 |
| 离线度量 | rd-kpi 脚本 + rd-retro | 每周 | 12 项 KPI 对比目标与上期；3 个会话的抽样评审 |
| 受控回归 | 基准任务 B1–B6 | C2 及以上改动前后 | 自动检查 + 流程检查，PASS/FAIL |

### 8.2 KPI（目标值的唯一出处是 scripts/rd-kpi.mjs 的 TARGETS）
| 编号 | 指标 | 基线 | 首月目标 |
|---|---|---|---|
| K1 | 平均每次请求的上下文 token | 319,202 | ≤ 120,000 |
| K2 | p90 每次请求的上下文 token | 626,255 | ≤ 200,000 |
| K3 | 上下文超过 200k 的请求占比 | 66.2% | ≤ 5% |
| K4 | 每条用户消息消耗的上下文 token（含子代理） | 21,260,527 | ≤ 8,500,000 |
| K5 | 每条用户消息的成本指数 | 24,288,174 | ≤ 10,000,000 |
| K6 | 工具调用失败率 | 1.9% | ≤ 2% |
| K7 | 每 100 次工具调用中超过 2 万字符的结果 | 2.8 | ≤ 1 |
| K8 | 每 100 次 read 中重复读取未变化文件 | 2.8 | ≤ 2 |
| K9 | 改了文件的任务段中已标注分级的占比 | 0%（新规则；41 个任务段） | ≥ 90% |
| K10 | L1–L3 任务段的最终回答带验收段落的占比 | —（新规则） | ≥ 90% |
| K11 | L3 任务段经过 review_agent 的占比 | —（新规则） | ≥ 90% |
| K12 | 用户消息中的返工信号占比 | 7.9% | ≤ 6% |

任务段 = 顶层会话中两条用户消息之间的部分，分级沿用会话中最近一次【L…】标记。K9–K12 依据回答中的固定标记与关键词统计，是趋势指标而不是精确度量；它们之所以可测，正是因为宪章要求固定格式。KPI 脚本附带合成日志的回归测试（scripts/test/rd-kpi.test.mjs）。

### 8.3 验收的定级标准
- **BLOCKER**：违反明确给出的 AC；构建或测试失败；安全漏洞；数据丢失风险。必须修复。
- **MAJOR**：很可能的缺陷或明显的可维护性问题；推断的 AC 不满足时最高定为 MAJOR。修复或写明理由。
- **MINOR**：风格与小建议，只列入报告，不阻塞。
- 没有证据的怀疑只能列为“疑点”；任务说明给出的改动清单之外的改动只在疑点中列一行，不定级。
- 结论：有 BLOCKER 为 FAIL；没有 BLOCKER 但有 AC 未验证为 UNVERIFIED（不能当作通过）；其余为 PASS。

验收员与作者是同一个模型，独立性来自三点：不继承作者的对话（spawn，而不是 fork）、使用不同的宪章与只读工具集、必须亲自重跑验证命令而不是采信报告。验收员只读：不改源文件与 git 状态、不装依赖；格式化与 lint 只用检查模式。

### 8.4 抽样评审
每次复盘依据 KPI 报告中的“抽样会话”表（上下文最大、返工信号最多、抽样各 1 个；只有结构化指标，没有会话内容），按 5 项各 0–2 分：分级是否恰当、AC 与证据、Token 纪律可由指标判断；改动范围与报告质量需人工查看（可选，用户按工作区与开始时间打开会话）。复盘代理不解码、不读取会话日志原文。评分只用于发现问题和生成提案。

### 8.5 Crisp 的角色
启用后，Crisp 的 JSONL 日志提供回答文风维度的外部信号（放行率、问题类型、评审 token），rd-kpi 会一并汇总。它是宿主层门禁，对所有模式生效。

## 9 持续进化闭环

### 9.1 流程
1. **收集**（每周一或用户输入 /rd-retro）：经 scripts/node.ps1 用 DSH 自带运行时运行 rd-kpi，读取上期报告、用户反馈文件 evolution/feedback.md、最近的变更记录与 Confluence 中的踩坑记录。
2. **诊断**：最多 3 个问题，每个都要有数值证据。
3. **提案**：写入 evolution/proposals/<日期>.md，格式为 问题｜证据｜改动 diff｜预期 KPI｜风险｜回滚｜等级。
4. **批准**：用户逐条选择 批准 / 修改后批准 / 拒绝；无人应答则不改。
5. **应用**：修改 → 校验（必须 OK；FAIL 时用 edit 逐处改回）→ C2 改动征得同意后用 set_bundle 关再开重新组合 → 新会话 /rd-selftest → 递增版本、记录 CHANGELOG、git 提交。
6. **检验**：下期 KPI 对照预期；连续两期未达标或出现退化则提出回滚提案。

### 9.2 变更等级
| 等级 | 范围 | 审批 | 生效方式 |
|---|---|---|---|
| C1 | 技能与参考文件的内容 | 可合并批准 | 技能目录被实时监视，下一步即生效 |
| C2 | 宪章、预设 YAML、工具与压缩配置 | 逐条批准，校验 + 自检 + 必要时跑基准任务 | set_bundle 关再开后的新会话 |
| C3 | 新增或移除插件、MCP、宿主设置 | 按 rd-ecosystem 流程逐步批准 | 视插件而定 |

### 9.3 防退化与防膨胀
- 校验器（scripts/validate.ps1）在每次改动后运行：YAML 方言、每个插件的配置 schema、未知字段、预设引用、占位符、技能格式与体积。KPI 脚本改动后运行其回归测试。
- 宪章改动优先写进 suffix（不超过 15 行），prefix 保持稳定以利用缓存；KPI 报告中的首轮请求中位数用来发现前缀膨胀。
- 基准任务在 C2 改动前后各跑一次，任何一张卡由 PASS 变 FAIL，或 token 增加超过 30%，都视为退化。
- 所有改动有版本号、变更记录与 git 提交，可以逐条回滚。

### 9.4 模型可以自主做与不可以自主做的事
- 可以：运行统计、写提案、在提案中起草技能与 diff、记录经验到 Confluence。
- 不可以（需要用户批准）：修改宪章、技能、预设配置；安装、启用或移除任何插件；修改 DSH profile 文件；推送代码。

## 11 风险、限制与未验证项
- **验收员与作者同模型**：独立性有限，由不同上下文、只读工具与强制重跑弥补；关键项目仍需要人工审阅。
- **压缩可能丢失细节**：199k 阈值是有依据的起点而不是最优值；若 K8（重复读取）明显上升，复盘时调整 retainTokens 或阈值。
- **K9–K12 是启发式指标**：依赖回答中的固定标记与关键词。
- **子代理预设出现在模式选择器中**：DSH 目前没有隐藏预设的字段；“研发·侦察”“研发·验收”也可以作为独立模式直接使用。
- **agentOptions 写死了 provider 与 model**（deepseek-account / deepseek-flash）：换账号类型或模型时需要改两处（INIT.md 排障表有说明）。
- **Crisp 可能也检查子代理的回答**（未验证）：放行率很高时影响可以忽略。
- **安全依赖指令**：当前权限为完全访问且不弹审批，红线只在指令层面生效；高风险仓库建议在会话中把权限切换为“工作区可写 + 询问”。
- **计划模式只能由用户进入**：模型无法自行进入，因此 L3 在非计划模式下用 ask_user_question 请求批准。
- **首轮固定前缀的实际大小未实测**：估计约 12–15k token（宪章约 4.1k 字符），一周后由 KPI 报告的首轮请求中位数给出实测值；它在缓存前缀中，约占目标平均上下文的 2%。
- **rd 作为子代理预设时宪章全文同样生效**：靠父代理在 prompt 中写明的子代理约定（只改指定文件，不分级、不委派、不提问、不提交）约束；子代理默认委派深度上限为 1，无法再委派。
- **Windows 下 read 只支持 UTF-8**：GBK、UTF-16 文本按宪章 §5.2 用 Get-Content -Encoding 读取，且不改写。
- **VS Code 的通用 YAML 插件会对 preset.patch.yml 报误报**（不认识 `!!js` 与 Cordis 补丁格式），以校验器结果为准。
- **官方预设随 DSH 升级变化**：本包标注 [shipped] 的行需要在升级后对照（INIT.md 7.3）。
