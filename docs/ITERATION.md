# 迭代协议

每轮优化都走同一条流水线，不做临场发挥。账本在 [ITERATIONS.md](ITERATIONS.md)。

## 每轮评估

结论别凭感觉写，先出证据：

```
node scripts/round-report.mjs <轮次>
```

它会跑体检与门禁，把「做了什么 / 验证数据 / 正向判据 / 结论」四段拼好，粘进 Issue 后逐项勾选判据。门禁有失败时它会直接说明「负面迭代不计入轮次」。

## 报告草稿自检

交付报告写完后跑 `node scripts/claim-audit.mjs --strict 报告.md`：每句「已完成 / 已通过」都要能指出是哪次运行。写了「未验证」的句子不报——承认没做不是虚报。

## 变更日志写法

条目里的并列用斜杠清单（`A / B / C`），不用密集顿号：顿号连排会被文案自检判为并列铺陈，分数掉到阈值以下。

## 记账

每轮的记账行末尾要写清这一轮用了哪个技能：`技能：rd-copy`，确实没用就写 `技能：无`。两者都不写的算漏记——`node scripts/skill-hits.mjs` 会按轮次统计命中率，漏记的轮次会单独列出来。

账本别手改，用命令：

```
node scripts/ledger.mjs --list 待做
node scripts/ledger.mjs --mark 022 完成 --issue "#58"
node scripts/ledger.mjs --append-round 43 "#58" ledger-cli "账本脚本上线"
```

## 开工前

新会话或中断后接手，先跑：

```
node scripts/resume.mjs
```

它会报出已完成的轮次、账本有没有跳号（跳号说明漏记，比进度慢更严重）、以及下一条待做。账本与代码不一致时先修账本再做新事。

## 一轮的九个阶段

| 阶段 | 动作 | 产物 |
|---|---|---|
| 1 复盘 | 读上一轮记录与本轮相关模块的现状：测试数、文档分数、告警、未完成项 | 一句话说明本轮要解决什么 |
| 2 选模块 | 从账本里挑一条未完成项；同一轮只动一个模块 | 本轮范围（文件清单） |
| 3 建 Issue | `github_workflow` 建 Issue，写症状、范围、验收标准、计划 | Issue 号 |
| 4 实现 | 只改该模块；先读后改，沿用既有结构与命名 | diff |
| 5 测试 | 跑该模块单测 + 全量 `node --test`；涉及文案跑 `aigc-check`；涉及密钥/提交跑对应脚本 | 命令与输出 |
| 6 提交 | Conventional Commits，窄行宽正文，`Closes #N` | commit |
| 7 推送 | `git push origin main`，推送失败就停下修，不跳过 | 远端确认 |
| 8 关闭 | `close_issue` 带验证证据；模块审计结果一并记录 | Issue 关闭 |
| 9 记账 | 更新 ITERATIONS.md 的状态、提交号、评估结论 | 下一轮输入 |

## 推送失败时的回退

`git push` 的 receive-pack POST 在某些链路上会挂起（`git ls-remote` 与 `gh api` 却正常）。
按顺序处理，不跳过、不改用别的交付方式：

1. 重试一次，确认不是瞬时抖动。
2. `node scripts/push-via-api.mjs --dry-run` 看要上传多少文件、是否会与远端分叉。
3. `node scripts/push-via-api.mjs` 走 Git Data API 推送（快进校验通不过就停下 rebase）。
4. `git fetch origin` 成功之后再 `git reset --hard origin/<branch>` 对齐历史：内容一致，提交号换成 API 建的那个。**fetch 失败时绝不能 reset**，否则会把本地提交清掉（本轮踩过，靠 reflog 恢复）。
5. 在当轮 Issue 里写明「API 回退推送」与实际提交号，别写成本地号。

API 推送的提交作者是 token 用户、时间为当时，只作回退；能走 `git push` 时仍用 `git push`。

### 两条硬规则

- **推送之后不要再 amend**：会造成本地与远端分叉；要改就新开一个提交，API 回退时用 `--parent <远端 sha>` 接在后面。
- **临时文件不进提交**：`.tmp-commit.txt` 这类文件先写、用完删，再 `git add`；否则会混进提交（本轮踩过，已 amend 去掉）。
## 什么算「正向」

一轮只有同时满足下列条件才计入迭代次数：

1. 测试数不减少，且新增行为有测试覆盖（`node --test` 全绿）。
2. 不引入新的告警、未处理错误或 TODO；不降低既有文档的 AIGC 分数。
3. 变更能用一条命令复现验证；没有「应该更快/更优雅」这类不可判定的说法。
4. 范围没有越界：只动本轮模块；跨模块改动拆成多轮。
5. 推送成功，远端能看到该提交。

任一条不满足，就判为负面迭代：不计入次数，下一轮必须重做同一目标或先修掉退化。

## 流程自查（每轮开工前 30 秒）

- **建单自查**：本轮 Issue 号是否已经存在？没有就先建，再动代码。第 4 轮漏过一次（先提交后补单），代价是要写一段说明。
- 推送自查：远端 sha 与本地树是否一致（`gh api .../git/commits/<sha>` 比对 `git rev-parse HEAD^{tree}`）。
- 账本自查：本轮条目状态与提交号是否已经改好。

## 账本字段

`编号 | 模块 | 目标 | 状态 | 提交`。状态取值：待做 / 进行中 / 完成 / 重做 / 取消（取消要写理由）。

## 节奏

- 一轮一个模块，小步推进；同一模块的多轮按依赖顺序做。
- 每 10 轮做一次横向检查：术语、文档与代码是否一致，测试是否变慢，宪章是否膨胀。
- 发现账本条目本身写错了，先改账本（作为当轮的一部分），再实施。
